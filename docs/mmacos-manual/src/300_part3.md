## SECTION 10: Reference

Part III is short by design. Its references already exist and are maintained with the code, so this
part points to them rather than copying them, and adds the one chapter the MACOS manual does not have:
how an assistant is expected to work with this library.

### Where the reference lives

- **The API catalog** is the Command Reference, Part II (`docs/macos-manual/cmdref/`, rendered as
  macosCmdRef). It is generated, and it lists every engine command with its MATLAB binding, the
  `macos.<name>` function that wraps it, and the test that exercises it. The help text of a `macos.*`
  function (`help macos.trace`) is the binding's own account, and the catalog is built from the same
  source (`macos_api_mod.F90`, read by the code generator).
- **The design rules and the agent guides** live in `MACOS_resources/optical_design/`. They are the
  equations and conventions of the design layer (`TELESCOPE_DESIGN_REFERENCE.md`,
  `SPECTROMETER_DESIGN_REFERENCE.md`), the coronagraph rules (`CORONAGRAPH_DESIGN_RULES.md`), the two
  agent guides (`OPTICAL_DESIGN_AGENT_GUIDE.md`, `CORONAGRAPH_DESIGN_AGENT_GUIDE.md`), and the regression
  fixtures the conic solvers are checked against (`fixtures/*.json`). Read them before changing any optical mathematics in the design layer.
- **The library's own record** is `MACOS_resources/mmacos/CLAUDE.md`. It covers the layering, the package
  conventions, the gotchas that were closed, and the test that pins each one. The design-layer and
  runner entries are the first thing to read before changing them.
- **The engine** is documented by the MACOS manual. Section 4 is the prescription language; Sections 5
  to 8 are the analysis commands that the bindings wrap.

### Working with the library: a chapter for the assistant

This chapter is written for an AI assistant asked to run, adapt or extend *mmacos*, and for the person
who sets one to work. It is the MATLAB reader's version of the MACOS manual's Appendix D. Read that
appendix too: it covers driving the engine directly, and everything it says about evidence holds here.

#### Where the facts live

- **The templates are the worked answers.** `templates/00_INDEX.md` lists them by thread, and Part II
  of this manual has a page for each. A request ("design an unobscured 3 m telescope") usually matches a
  template whose parameter block already has the knobs. Adapting a template beats writing a new script.
- **The runners in `design/runners/` are the product**, and the stage scripts of a template are thin
  narrative drivers over them. A runner's help text states its inputs (the `.in` prescription plus the
  sidecars it declares) and its artefacts.
- **The test suites are the specification**: `mmacos/tests/` (run by `run_mmacos_tests.sh`), the
  engine's `cli_tests/`, and the *pymacos* suite. A behavior no test pins is not yet a promise.
- **A template's README is a record of its last run**, not a guarantee of the next. Part II found
  READMEs whose tables predate the engine they run on, and templates whose defaults are not the inputs
  of the run their README quotes. Run the template, then compare.

#### Driving it

- **Start each MATLAB session with `run('<path-to>/mmacos/mmacos_setup.m')`.** It puts `src`, the design
  layer and the sensitivity helpers on the path, anchored to its own location. Templates are not on the
  path; `addpath` the one you run.
- **Run a template on a copy when its outputs are not yours to commit.** Most templates write their
  decks, reports and figures beside themselves, and some write further. One stage script of the e2e
  thread writes a library preset (Section 5 says how this manual handled it). Before running a stage,
  search it for writes outside its own folder.
- **The model size is the first decision.** `macos.init(N)` fixes the largest ray grid of the session.
  It must be at least the prescription's `nGridpts`: below that, the engine resets the grid with a
  message and can crash later. Changing size within a session is not reliable, so use one size per
  MATLAB process.
- **Trace before you read.** `macos.opd`, `macos.intensity`, `macos.complex_field` and `macos.dx_at` read
  the state a trace leaves, and a modification wipes it. A perturbation (`macos.perturb`) is not seen by
  the next trace until `macos.modify()` marks the prescription changed: without it the change reads as
  zero (Section 6).
- **Session modes survive a load.** POLARIZATION, VECTOR diffraction and the OPD reference persist across
  `macos.load_rx`, and the binding warns at every load while one is in force. Set them deliberately,
  per measurement.
- **The OPD reference decides what a wavefront comparison measures.** The engine's default is the chief
  ray; some runners harvest at the aperture mean. Section 6 shows a 188.9 nm "disagreement" that was
  entirely a reference mismatch. Put both sides of any comparison on the same reference, and say which.
- **Units:** translations are SI metres at the binding. `trace().rmsWFE` and `macos.opd()` are metres,
  not waves, and the `dw_dx` translation columns are per base unit by default. Read the help text's
  units line before you convert.
- **Headless runs** go through `matlab -batch "...; exit(0)"`, with the exit in the command, not inside
  the template. A batch MATLAB that has loaded the mex can hang at an implicit exit. Kill a hung one by
  its process ID.

#### Conventions that bite

- **Mirror signs.** The design layer emits `KrElt = -|R|` for every mirror; the concave or convex sense
  is in the geometry, not the sign. An off-axis section's `VptElt` is the parent's vertex; ask
  `Bench.station` where an element really sits.
- **Grid files.** A `GridFile=` is read from the working directory at load, and its lines are columns, so
  a naive MATLAB `load` gives the transpose. Run with the working directory set where the grid lives.
- **Numbers that are numerically zero** (a collimated system's rms near 1e-12, a chief-ray coordinate
  near 1e-11) share no digits across machines. Pin a real signal to five significant figures; bound a
  numerical zero in magnitude, and check the bound.
- **A large linear model** has quadratic forms that are computed as `trace(P*G)` with `G = D'*D`, never
  as the outer product `D*P*D'`, which runs out of memory on a tall Jacobian.

#### Working rules

These are the house rules this project holds its own assistants to, each one learned the hard way.

1. **Measure before you guard.** Before adding a check, find the value's other writers. Guards warn and
   count; a new refusal of behavior a long-standing tool tolerated needs the maintainer's decision.
2. **Every fix ships with a test that fails before it.** A test that cannot fail measures nothing, and a
   toy input that bypasses the code path is not a test of it.
3. **A gate that cannot measure must refuse, and must ship with a case that passes.** A gate that fails
   open looks like it works. This manual's own bound pins once printed a bound they had not checked.
4. **One parameterized runner per system**: a `<sys>_params` sheet and a `<sys>_run` driver. A number in
   the sheet was chosen; a number in a report was derived.
5. **No `exit` inside an example.** The batch wrapper supplies it. Save the inputs and the outputs
   (the `.in` and a `.mat`) beside the example, and give every design an accessible exit pupil
   (`add_pupil`).
6. **Figures are the tool's own output, unmodified.** Look at every figure before printing it. A figure
   producer can rot silently, and this manual found legends and charts that misstate their data. Say so
   in the caption rather than redraw.
7. **Read the frame before calling a mismatch**, and **look at the raw per-ray data before blaming a
   solver**: a histogram of per-ray OPD finds what an outlier cut hides.
8. **Characterize before another ladder.** After two failed hypotheses, read the residual's structure
   before trying a third.
9. **Report outcomes faithfully.** A number comes from a run on a named build with the prescription and
   commands that produced it. Quote it from the run's output, never from memory. A failed test is
   reported with its output, and a skipped step is reported as skipped.
10. **Write the resolution where the next reader will find it**, at the time it is resolved: in the
    template's README, the library's record, or the plan's findings list.

  compare the result with its README before telling me anything."*
